# 解释行为：逐条结构复核、旧评审轨迹及评分交付边界

日期：2026-11-07，Asia/Shanghai。操作者：已见项目、条件和作者判断的助手。此记录是知情复核，不是独立评审、语义金标准、正式批准、采集协议或新的模型结果。

## 一、48条输入逐项结构

[48行结构表](item-structure.csv)按每条列出目标单位/字段、目标赋值、冲突归属、规则和填充槽位及三条赋值所在文档；它直接暴露条件和协调信息，只供协调端使用。三条赋值来自[固定原文](../2026-11-06-explanation-scope-materials-v2/materials.json)，一格代表一条实际材料，不是回答或评分。以[独立于原生成器的只读脚本](../../../scripts/audit_explanation_scope_items_20261107.py)解析固定问题、五个完整文档的受限语法、全部赋值及规则；逐项核对作者文件中目标和其他单位同字段引文的文本、槽位和覆盖，核对12对I0/IU的单槽差。基于所用模板的助手知情判断，S各一条目标赋值、I0各无目标赋值且无记录冲突、IU各无目标赋值且另一单位同字段冲突、CT各两条目标冲突赋值。没有发现预定结构与实际记录不一致。

检查结果与[作者原判断](../2026-11-06-explanation-scope-materials-v2/author-interpretation.json)对应，但脚本只是解析已知固定模板并验证证据引用，不能判定全部自然语言解读或消除作者暴露。单一S记录在规则允许记录不可靠时只构成记录相对支持；保守怀疑世界真值的回答不等同于文本蕴含现实真值，该区分在未来按冻结S端点评分时必须披露。对于IU，其他单位冲突不使目标字段出现互斥记录；对于CT，按规则目标两记录相互冲突但不提供来源优先级。局部修复见证不是对世界事实的认证。

运行 `python3 -B scripts/audit_explanation_scope_items_20261107.py > /tmp/scope-items.csv` 输出相同表；本轮两次运行与保存表逐字节相同。四项临时突变检查分别对额外句子、S目标字段变更、引文不匹配和重复ID拒绝；这些检查仅验证本脚本的有限结构拒绝能力。模板一旦变化应停止检查并审查新版本，不把脚本失败改写为语义错误率。

## 二、旧CLI可见命令的重新核对

[审计结果](cli-visible-commands.json)保存三份已归档轨迹SHA及31个保留的`item.completed`命令事件的命令文本哈希、状态和有限词法标记。其中29个成功、2个失败；标记检查未识别字面父目录、指定绝对路径、网络或Git读取命令。唯一`subprocess`标记是本地执行`validate_claim_review_metadata.py`。这支持此前记录的29个成功命令的观察，但并不证明进程没有通过间接调用访问其他文件或网络；脚本搜索不是OS审计。源轨迹本身标注部分事件类型被省略，不将31个保留命令当成完整系统调用史。

五类先前项目暴露未见是评审自述；输入记录先封存、再记录第二阶段交付，有可复核的SHA/时间证据。记录初始审计`can_proceed=false`及后续说明其为等待任务，不覆盖原始值。memory开关的观察发生在第二阶段之后；第一阶段协调者`recorded_at`比评审自述完成晚，且该字段不标称实际交付时刻，因此不能由它重建精确交付时刻。复核结论为“可见证据支持受限流程隔离，未发现上述字面路径访问”，不是完整私有上下文认证、独立性的正式批准或语义正确性证明。

旧草案规定上下文独立性和焦点结论需满足条件后才能采纳为采集研究；本轮继续保留`context_audit_pending`及正式批准0。用户授权助手继续工作并不改变评审实际来源。要形成正式协议，必须先明确可接受证据、批准主体和对不可观察历史的处置；目前这些没有在冻结草案中形成可自动判定的通过记录，不能由汇总脚本或本助手知情复核自发生成通过标志。

## 三、原自由回答指令的限定

旧P0指令在证据不足时要求说不足且不猜；还明确要求当文档对**问题**给出不兼容答案时报告冲突且不选边。此次设计沿用该指令，“不新增冲突诱导”只表示不在P0之外添加新提示，不能说模型从未收到关于冲突的指示。若未来得到IU−I0差异，只能解释在这一既有指令、该模板、模型和解码设置下的局部行为，不宜外推到未提示冲突的问答。具体原文及指纹绑定见[旧参考协议快照](../2026-11-06-explanation-scope-cpu-preflight-v1/relation-reference-snapshot.json)和[执行预案](../2026-11-06-explanation-scope-cpu-preflight-v1/execution-draft.json)。

## 四、未来回答评分包：信息分离方案

[review_artifacts](../../../scripts/explanation_scope_runtime.py)已经把完整匿名`packet`、`coordinator_mapping`和`endpoint_template`分别返回，并明确警告后两者暴露条件。端点模板包含`scene`、`condition`和关联`source_item_id`，因此**不得发给未暴露条件的逐主张评审者**；[48行结构表](item-structure.csv)亦不得发给该评审者。现有上轮[条件性草案](../../explanation_scope_precollection_review.md)提到的“评分包”应解释为仅`packet`可作为无显式条件标签的输入，不能把整个返回对象或端点模板当作盲审包。

可审查的阶段性操作如下，真实回答尚不存在，本轮没有创建真实评分：

1. 完成并验证48条技术记录之后，协调者保存packet和其哈希，独立保存mapping与endpoint_template；检查发给评审的文件、指令和路径，不包含条件标签、设计锁、作者解释或映射。匿名题目/文档本身可让评审推断材料结构，不能宣称条件不可被推断。
2. 评审只依据完整问题、五篇文档及回答，逐条写其本人对目标实体/字段、目标是否给值、缺口或冲突涉及何实体/字段的判断，并拆分全文主张。每项主张保存回答原文和字符跨度、支持/反证的文档槽与原文引用、支持/未支持/反证/歧义及理由；没有解释和不确定性分开记录。逐条声明接触过的材料与其他背景。此阶段的原始表不含协调者分配的S/I0/IU/CT标签，也不按条件适用性强行填W/E。
3. 在查看映射或作者解释前保存原始表、完成时间和字节哈希。之后由协调者按映射和已冻结规则把逐主张判断转换为W/E、S、CT及解释字段；如转换依赖新的知情判断或与原判断不一致，记录裁定者、理由与暴露，并保留两种判断。原始逐主张审核和之后的知情转换不是同一个独立性等级。
4. 将技术完整性、input/output哈希与记录逐项核对后填已有端点模板，汇总器再计算结果。汇总器只核声明格式、不读取原始输出与引文或认证独立性；正式研究报告必须同时保留原始引文及来源审计，unknown和未审不得自动变no。

这是在现有工具行为下整理的手工信息分离流程，不是已执行的评审，也不声称已完成独立评分或接收程序。实际协议如果需要另一种阶段顺序、额外审查或工具支持，应在任何回答生成前另版固定并审查，不修改已冻结协议以追认结果。
