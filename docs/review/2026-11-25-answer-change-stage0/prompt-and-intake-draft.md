# 两路线提示及评审接收草案

状态：开发草案；不是固定协议、运行入口或模型调用记录。将来使用前必须固定实际模型、完整材料、参数、预算和版本；先对已暴露材料检查，再冻结用于新规则的版本。两路线必须使用相同证据与题面，不共享会话或对方输出。

## 公共输入框架

以下是完整的题面、限定的可能事件日期范围和供本次任务使用的证据。仅依据这些材料回答；证据不足时明确说明，不能虚构证据或引用。每个证据段保留其标识，以便引用。用户对回应方式的要求写在题面中。

```text
题目：{question}
可能的事件日期范围：{date_range}
证据：
{evidence_with_ids_and_version_metadata}
```

其中范围与元数据必须直接交给所有路线；材料清单、顺序及原文按题固定。禁止输入知情参照、正确类别、配对另一题或评分标签。

## 路线 A：直接回答

> 根据给出的题目、日期范围和证据，回答用户的问题。说明与结论有关的依据并引用证据标识；如果无法给出无条件的唯一结论，请按题目允许的方式提供有用的回应。

## 路线 B：逐版比较后回应

> 先分别列出题目限定范围内各个相关版本的适用日期、针对题目事实的结论及支持该结论的证据标识；再比较这些结论，按题目要求回应用户。若某个版本缺失、适用范围不明或证据不足，请标明，不要猜测。

两路线只改变任务指令，预定同等模型和输出上限；真实输出上限须在开发中检查不会系统性截断逐版回答后锁定。应保存完整可见输出、完整输入或其受限归档、模型标识、版本、输入输出 token、起止时间、EOS／截断、错误和计费。各自重新建立独立会话；同题不同状态不共用历史，防止题目配对泄漏。无输出或失败保留，不静默重试；如有技术重试，记全部 attempt 并预定分析口径。提示不要求特定 JSON 格式，但要求可核对的来源标识。

## 核心评审表字段草案

逐输出至少记录：匿名输出 ID、规则／配对／情境 ID、实际可行日期、日期是否已知、材料覆盖、检索是否可用、任务要求、作者参照版本、输出文件哈希、评审人及其暴露、实质行为、无条件唯一主张、明确或可由完整分支蕴含的唯一性判断、逐版结论与引用、引用逐字存在、引用语义支持、追问是否有效、补日期后结果、截断及错误、unknown 理由。每项保留判断依据、必要原文引用与复核分歧。

评审包去掉路线和模型标识，随机顺序；协调映射单独封存。仅通过换 ID 或同一知情会话无法证明评审真正盲化。法律参照应由独立具备判断能力的人核验；答案评分和法律参照复核是不同角色，均记录身份与暴露。未能实现时明确称知情评审，不以另一会话或程序自动声称独立。

## 接入现有抽取路线

只读检查发现[冻结入口](../2026-11-25-role-assignment-holdout-v1/run.py)依赖四段、两段可解析不重叠版本及作者整理的范围断言和来源。需定义原有动作、逐版结论及引文到统一评审表的逐字段映射；只复制或确定性展开现有输出，禁止补写缺失内容。检查同一人工整理范围断言能否同等提供给所有路线；若范围来源或角色由作者预先标出，标记人工辅助和信息不对称。必须先在已暴露材料验证适配，并报告结构差异和失败；不得因适配困难更改算法后仍称冻结路线。此映射尚未实现。

## 试运行前检查

确定模型与运行通道；各项来源用途与外发范围；实际合法参照复核资源；证据区间完整性；提示、token 预算和失败策略；盲评或知情评审的真实状态；成本和 GPU 用户执行准备。完成前不得称试运行已就绪。
